# 已知问题

## CLI 单轮 Token 消耗和执行时间偏高

- 记录日期：2026-09-18
- 状态：`MITIGATION_IN_VALIDATION`
- 当前优先级：低于正式梗产出质量与跨轮稳定性
- 影响范围：使用 Codex CLI、Playwright MCP 执行完整 AUTO 轮次

### 现象

2026-09-18 连续执行了 3 轮真实 AUTO 稳定性测试。三轮均正常到达
`H02 / WAITING_HUMAN_EVALUATION`，但资源开销较高：

| 指标 | 三轮合计 | 单轮平均 |
|---|---:|---:|
| 输入 Token | 13,148,037 | 4,382,679 |
| 缓存输入 Token | 12,620,544 | 4,206,848 |
| 非缓存输入 Token | 527,493 | 175,831 |
| 输出 Token | 103,580 | 34,527 |
| 实际墙钟时间 | 约 41.3 分钟 | 约 13.8 分钟 |

缓存输入约占总输入的 96%。账面输入 Token 不等同于全部按非缓存价格计费，具体费用取决于所用模型服务的缓存计价规则；但上下文体积仍会影响执行时间和运行可观测性。

### 已观察到的主要来源

1. Playwright 搜索和正文定位会返回较大的 DOM/可访问性信息，后续模型回合会继续携带这些历史结果。
2. 完整轮次包含 42～49 个节点，单一主管需要持续维护跨节点账本。
3. 每个隔离 CLI 轮次会重新加载 Skill 及相关参考文档。
4. 最终完整机器记录由模型集中整理和写入，三轮均出现约 4～6 分钟的尾部静默窗口。
5. 当前环境中的 Google 探针连续失败，随后才回退到百度，带来额外调用和等待。

### 当前决策

已采用“短生命周期搜索 worker → 程序化差异覆盖与精简交接 → 无网络主管生成”的缓解方向。仍优先保障：

- 完整原梗边界可核验；
- 真实变式逐字可追溯；
- 模板和槽位契约准确；
- `凿agu` 施受关系、中文自然度和原梗辨识度；
- 正式梗产出质量稳定；
- 强制停在人工评价门。

任何性能优化都不得通过减少证据门禁、放宽严格变式定义、跳过适用性审查、缩减必要的候选质量评审或取消人工评价阻塞来实现。

### 已验证实验与剩余边界

固定原梗实验中，初版 worker 仅按证据数量停止，虽显著降低 raw Token，却漏掉动作尾槽差异并造成生成退化；加入高价值差异覆盖与百度定向 micro-worker 后恢复了最小替换质量。最终版本必须继续通过多组隔离回归，不能把单个受控案例当成稳定性结论。

当前实现：

- worker 禁止全页快照，只取短搜索卡片和命中正文；
- 程序去重、裁剪、计算真实差异覆盖并汇总子会话 Token；
- 数量门槛之外增加生成高价值位置覆盖门禁；
- 中文精确短句定向补证优先百度，减少无效引擎探针；
- 主管只接收不超过 16KB 的精简证据包。

### 未来验收原则

只有在固定回归集和真实 AUTO 多轮测试中确认正式梗质量、证据完整性和状态机合规性均不退化，才能接受性能优化。Token 与耗时改善应作为次级验收指标，不能覆盖质量回归。
